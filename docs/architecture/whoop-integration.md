# WHOOP integration architecture

FitCore currently runs on TanStack Start and Vercel. Tracking history, settings, and backups use the existing browser persistence layer. WHOOP requires a server-side token exchange, durable credentials across invocations, and authentication for every operation that could expose private data. The WHOOP session should be independent of core workout logging.

## Recommended first release

Use FitCore's existing Vercel functions and a dedicated Neon Free Postgres project for the integration. For the first, single-owner release, generate a random 256-bit FitCore integration access key locally. Vercel holds only its digest, and successful entry issues a 30-day opaque session in a Secure, HttpOnly cookie. Postgres stores a digest of the session token. Lock removes the session, and rotating the access key invalidates every existing session. An independently managed identity provider is the better extension for multiple users or account recovery. It would add another sign-in flow and provider for this single-owner release. A browser-only OAuth flow would expose confidential credentials or require abandoning background sync.

Neon Free currently includes 1 GB of Postgres storage, 100 compute-unit hours per project per month, and a six-hour instant restore window. Use a separate project with synthetic data for preview verification and a private schema with a least-privilege application role. On Vercel Hobby, start with app-open and manual sync. Hobby is for personal use. Evaluate scheduled reconciliation after the foundation is verified, including Hobby's schedule constraints. [Neon Free](https://neon.com/blog/neon-free-plan-1-gb-per-project) · [Vercel Hobby](https://vercel.com/docs/plans/hobby) · [Vercel cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing)

## Connection and credentials

- Start via a same-origin POST from the authenticated integrations panel. Bind a short-lived authorization attempt to the initiating session and a separate random browser nonce carried in a Secure, HttpOnly, SameSite=Lax cookie. Use WHOOP's documented eight-character state and atomically claim it once. Resolve the callback to the same active owner and pending attempt before saving credentials. Match the configured HTTPS origin and fixed callback path. If the browser context changes on iPhone, restart the flow from an authenticated context and have the installed app read only its owner's connection status on resume.
- Exchange the code server-side using the registered redirect URI. Redirect to a clean, fixed route and suppress caching, referrers, and sensitive application logging. Vercel's request logs can show query parameters, including WHOOP's short-lived authorization code and state. Review synthetic deployment logs and access controls before any real connection, including whether a log drain forwards the callback query string. The Client Secret, access and refresh tokens, and health payloads stay out of request URLs and logs. [WHOOP OAuth](https://developer.whoop.com/docs/developing/oauth/) · [Vercel runtime logs](https://vercel.com/docs/logs/runtime) · [Vercel drain log schema](https://vercel.com/docs/drains/reference/logs#logs-schema)
- Request read:recovery, read:sleep, read:cycles, read:workout, and offline. Recovery, sleep, cycle, and workout responses supply the needed metrics and source identifiers. Defer read:profile and read:body_measurement. WHOOP documents step count on cycles when available. [WHOOP v2 API](https://developer.whoop.com/api/)
- Store tokens as an authenticated encrypted pair with a server-managed, versioned encryption key and owner identity bound to the ciphertext. Keep credential tables and application writes private to the server. Serialize refresh per connection and commit the new pair together with the expiry. If the provider may have accepted refresh before a timeout or crash, mark the connection for reauthorization when a safe outcome cannot be established. Avoid retrying a potentially spent refresh token. Fence refresh and sync finalization against disconnect and reconnect.
- For disconnect, immediately disable synchronization and delete imported data. Revoke via DELETE /developer/v2/user/access using a valid access token. Surface a revocation failure and document the WHOOP-side removal option if credentials are unusable. Keep imported data and credentials outside FitCore tracking backups in the first release. Document the database backup retention period before using real data. [WHOOP revocation endpoint](https://developer.whoop.com/api/)

## Synchronization and dashboard

Rebuild the rolling 30-day WHOOP snapshot from all pages of the four v2 collections. Record the successful sync time only after all four collections finish. A failed or incomplete import leaves any unexpired prior snapshot available. Complete collection reads reconcile deletions and corrections inside the window, and source IDs and update times prevent duplicates. Manual sync and app-open sync share one database lease and a two-minute cooldown. Respect rate-limit headers, back off transient failures, and advance last successful sync only when a complete intended sync commits. Display missing, pending, and calibrating values as such. Keep WHOOP Recovery distinct from FitCore Readiness. Link workout activities only when timing and type make a match unambiguous. Keep WHOOP_JARVIS_SHARING_ENABLED unset for live use until the intended AI-provider use has been confirmed under the October 2026 WHOOP API Terms. Jarvis requests omit WHOOP by default. The option in the Jarvis composer authorizes one typed message and resets after use. The server checks the active WHOOP session, sends only recent measured values and dates to the named provider, and limits the reply to read-only tools. FitCore clears WHOOP-derived replies when Jarvis closes, the tab is hidden, or the WHOOP session locks, disconnects, or expires.

The optional v2 webhook endpoint authenticates the timestamp and raw body against the WHOOP client secret and deduplicates events for the provider ID learned from sync. It acknowledges accepted events before fetching. Vercel can run the same bounded sync after acknowledgement. Signed deletions received before the first import are held by provider ID and applied only to the matching WHOOP account. Deleted records are removed from the live snapshot immediately. For up to 31 days, the deletion record prevents stale API responses from restoring the measurement. A newer update timestamp from a later authenticated WHOOP API read can restore a regenerated record. If an event arrives during cooldown or background execution fails, app-open sync or the daily reconciliation can catch up. The Vercel Hobby cron runs in the 10:00 UTC hour and does a full 30-day reconciliation even when there were no webhooks. [WHOOP v2 webhooks](https://developer.whoop.com/docs/developing/webhooks/) · [Vercel cron limits](https://vercel.com/docs/schedules/cron-jobs/usage-and-pricing)

## Configuration handoff

Keep the registered redirect at https://gym-app-jade-eight.vercel.app/api/whoop/callback and privacy URL at https://gym-app-jade-eight.vercel.app/privacy. In the WHOOP Dashboard, keep the Recovery, Cycle, Sleep, and Workout permissions. The authorization code requests offline renewal. Remove Profile and Body Measurement unless WHOOP requires them for a later feature. Leave webhooks disabled during the initial release.

FitCore checks Cache-Control, Age and Date on every page. A missing freshness lifetime or a no-store or no-cache directive limits the complete response to display in the requesting browser. FitCore limits the display to two minutes or the shortest positive upstream freshness deadline. It clears on hide or lock and rechecks the connection and webhook revision while visible. No measurement fields from a transient response reach Postgres, tracking backups or other tabs. A database snapshot requires WHOOP_SNAPSHOT_CACHE_ENABLED and a configured cleanup cron. It uses the shortest upstream freshness deadline, less a 32-hour allowance for the daily cleanup and database recovery copies. FitCore serves the resulting snapshot for up to 24 hours. If scheduled cleanup is turned off, clear existing snapshots and their expiration timestamps as part of the change. Leave WHOOP_SNAPSHOT_CACHE_ENABLED unset until deletion timing can be verified even if the daily cron fails. Confirm the actual WHOOP cache directives and data-use terms before approving live configuration. Confirm an accessible support contact and the at-rest encryption and recovery-copy behavior for the selected database plan. [WHOOP API Terms of Use](https://developer.whoop.com/api-terms-of-use/)

After synthetic verification and security review and with production configuration approved:

1. In the dedicated Neon project, run the migrations db/whoop/001-credentials.sql, db/whoop/002-sync.sql, db/whoop/003-webhooks.sql and db/whoop/004-cache.sql in order using the migration owner. Create a separate login role and grant USAGE on the fitcore_whoop schema and SELECT, INSERT, UPDATE, DELETE on sessions, oauth_attempts, connections, and webhook_events only. Use this limited role's connection string for Vercel. Do not expose the schema with a browser-facing Data API. The free instant restore window can retain deleted rows for up to six hours.
2. In Vercel Dashboard > gym-app > Settings > Environment Variables, select Production. Set WHOOP_ORIGIN to https://gym-app-jade-eight.vercel.app and WHOOP_CLIENT_ID to the client ID from the WHOOP Developer Dashboard. Add WHOOP_CLIENT_SECRET with the value from the WHOOP Developer Dashboard and mark it Sensitive. Use the Vercel dashboard for secrets. The FitCore owner access key is separate from the WHOOP Client Secret.
3. Set WHOOP_DATABASE_URL to the limited-role connection string. Set WHOOP_TOKEN_ENCRYPTION_KEY to an independent 32-byte random key encoded as unpadded base64url. Mark both variables Sensitive. Keep a separate password-manager copy of the encryption key to avoid losing access to stored credentials.
4. Generate another independent 32-byte base64url value for the FitCore owner access key. Save this value privately in your password manager. Hash the exact base64url text with SHA-256 and set WHOOP_OWNER_KEY_SHA256 to the lowercase hexadecimal digest as a Sensitive variable. FitCore expects 64 hexadecimal characters for the digest. Keep the raw key for the iPhone sign-in form.
5. Keep WHOOP_INTEGRATION_ENABLED unset during synthetic tests and while deployment approval is pending. Set it to true only for the approved production deployment that enables the integration. Review preview environment scoping and runtime logs with synthetic values. [Sensitive environment variables](https://vercel.com/docs/environment-variables/sensitive-environment-variables)

For the separately approved background rollout, add a random CRON_SECRET (32–128 URL-safe characters) as a Sensitive Production variable in Vercel. Set WHOOP_BACKGROUND_ENABLED to true and deploy the configuration with a daily cron at /api/whoop/reconcile. After a successful initial sync, register https://gym-app-jade-eight.vercel.app/api/whoop/webhook in WHOOP Developer Dashboard > your app > Webhooks with model version v2. The app uses your existing WHOOP Client Secret for signature validation. Confirm synthetic valid and invalid signatures and the signed cron request before connecting real data. [Vercel cron authentication](https://vercel.com/docs/schedules/cron-jobs/manage-cron-jobs#securing-cron-jobs)

After approval and deployment, open Settings > Integrations & Devices > WHOOP in installed FitCore. Enter the FitCore owner access key to unlock the integration, then tap Connect WHOOP and authorize on WHOOP. Confirm that it returns to the app or that the installed app shows the same connection on resume. Test cancellation and an expired session with synthetic authorization before the real account test. Confirm Sync Now, data values against WHOOP, and offline workout logging on the physical phone.
