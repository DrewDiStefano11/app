# Owner-authorized WHOOP archive

Migration `006-owner-archive.sql` introduces a private archive separate from the temporary, provider-header-limited snapshot cache. It creates **no consent** and changes no environment flags. The server integration requires both `WHOOP_OWNER_ARCHIVE_ENABLED=true` and `WHOOP_ARCHIVE_DELETION_POLICY=no-recovery-copies-v1`, with the latter set only after verifying the database's recovery-copy/deletion configuration. Settings offers explicit consent, export and withdrawal. Successful dashboard syncs commit to the archive and the existing shared records endpoint restores it before provider refresh; Jarvis remains separately gated. Resumable history import and production activation remain subsequent work.

Consent binds an authenticated FitCore owner, current connection and verified WHOOP account. The versioned purposes are personal display, history and fitness analysis; they do not authorize transmission to AI providers. Grants preserve their original timestamp until withdrawal. Reauthorization after withdrawal creates a new consent identity without reviving prior records.

Normalized records use stable consent/type/provider-ID keys. AES-256-GCM payloads use a domain-separated key derived from the existing encryption master. Authenticated context binds owner, connection, provider account, type, ID and provider revision. Identity/time/index metadata stays in the private database; measurements remain encrypted. Native WHOOP units are milliseconds for durations and HRV, beats/minute for heart rate, percent for recovery/sleep performance, and the provider's numeric strain scale. `whoop-v2-native` versions these units.

Each complete sync batch holds the existing connection lease and event-revision fence, upserts only same-or-newer provider revisions, stamps success, and releases the lease in one SQL statement. Failure rolls back the whole statement. Empty successful responses retain earlier records. Reads require an active owner session, connected matching provider account and unrevoked consent; the display lease ends at session expiry, independently of provider cache headers. Current-measurement freshness rules remain enforced by existing evidence selectors.

Database triggers erase records, import checkpoints and tombstones on withdrawal/disconnect; deletion webhooks remove matching records and dependent recoveries. Archive tombstones outlive temporary webhook receipts to prevent historical reimport of deleted revisions. Newer provider corrections can supersede a tombstone. The archive cannot be read while a connection requires reauthorization. No archive-specific logs or unmanaged backups are created.

Before production activation: apply the migration and separate least-privilege grant script, verify deletion behavior and resolve managed restore history/replica/snapshot retention. The observed dedicated Neon project has a six-hour restore window, one branch, no read replicas and no manual snapshots. Production remains live-only until those changes are deployed and verified. Managed physical deletion can be asynchronous; disabling restore history removes the application's ability to restore withdrawn records and does not claim immediate disk sanitization. On API termination disable access and run the reviewed `operations/terminate-access.sql` as migration owner; verify applicable managed copies are removed as well.

Acceptance uses the actual built Vercel artifact, HTTPS owner-session cookies, production archive flags with the temporary cache disabled, the Neon HTTP client and actual SQL/encrypted disk persistence through PGlite. External WHOOP responses are synthetic. The test closes the whole browser engine, reopens the database files, starts a new engine and checks restoration while provider requests are held, then automatic replacement, failure preservation, deduplication and consent withdrawal. It does not establish hosted Neon configuration, production activation or physical iPhone acceptance; those require deployment verification and the owner's device check.

Policy basis: [WHOOP API terms](https://developer.whoop.com/api-terms-of-use/), effective October 6, 2026, §4.2 expressly permits data-owner authorization to qualify its listed restrictions. This design scopes that basis to the owner's personal normalized measurements and numeric results; it does not grant rights in unrelated content, algorithms or third-party IP (§4.1), remove security duties (§2.4), or waive termination/discontinued-access deletion (§7.1). Operator termination must stop access and erase the archive and applicable recovery copies before archival use resumes.
